# 独立消费者接入评审

## 怎么测的

`examples/quickstart` 是独立 Maven 项目，只依赖安装后的库 JAR。测试不引用库的测试类，不读取 Redis 内部 key，也不调用 Lua。每个“节点”是独立 JVM，每个进程在本地保留任务，拿到令牌后通过 HTTP 提交；Python 测试服务记录每次实际到达的请求。

运行方式：

```bash
python3 examples/quickstart/run.py --scenario all
```

脚本启动临时 Redis，不连接生产环境。场景包括三节点轮转、空闲节点、30 节点两张表、真实 75／15s 窗口，以及业务 503 后重新取令牌的重试。

## 结论

库适合作为分布式操作前的公平额度获取组件。独立接入验证了任务最终完成、成功操作不重复、每次 HTTP 尝试都有新的获取记录、多资源可分别推进。这里没有发现确定的令牌超发，但也不能仅凭这些外部观察证明所有微秒边界；库自身的 Lua/真实 Redis 测试负责精确边界验证。

需要明确区分：**令牌发放窗口与下游收到请求的窗口不是同一个观测点。** 本地 Java 8 的压力重试场景曾记录到 4 次 HTTP 请求相隔 998.102ms，而库的窗口配置为 3／1s。进程调度和请求传输可以改变到达间隔。报告保留这一现象并标记 WARN，不把它归为下游限额通过，也不据此直接推断 Redis 超发。

Java 21 的 `window` 场景还观测到 HTTP 峰值 76／15s，而发放区间的检查没有无法判定的边界组。这进一步说明：把获准时间的限制直接当成下游接收时间的保证不成立。

采用 `rate=2.5、burst=1、window=3/1s` 的重试对照满足本地观察的 HTTP 窗口；30 节点场景采用 `rate=4.8、burst=1、window=75/15s`。速率余量需要按实际环境选择，不能据本地通过就承诺任意网络延迟下的服务端窗口。

## 已落地的接入改进

| 接入时的问题 | 调整 |
|---|---|
| README 先讲大量业务背景，首次接入者很难找到启动步骤 | 首页缩为用途、已确认的图、一条运行命令和一个 API 片段；业务细节迁入独立文档 |
| 只有获取片段，不清楚 WAIT 后怎么处理任务 | 独立消费者保留同一个任务，按建议时间重试，等待一张表时仍可处理另一张表 |
| 容易在拿到一次令牌后反复重试业务 | 用 FairGrantExecutor 包裹一次 HTTP 尝试；收到明确的业务失败后，重新获取新额度 |
| 无任务节点可能错误登记，挡住队首 | 示例明确只为就绪任务登记，空闲节点测试检查它不挡住另外两个节点 |
| 单看“测试成功”容易混淆令牌计数和真实调用 | 分开报告任务结果、HTTP 窗口峰值、可确定的发放窗口冲突和无法判定的边界组 |
| 多进程测试需要手动起 Redis、启动 JVM、清理进程 | 一条脚本自动构建、运行和关闭临时服务；日志持久保留 |

## 还需要接入方处理的事情

- 当前没有 Maven Central 正式版本，首次使用需构建安装；脚本代办此步骤。发布正式制品是后续降低接入门槛的一项工作。
- 库不管理线程调度、任务存储或业务幂等。示例使用专用调度循环；生产代码应接入现有任务调度器。
- 这里的 503 是明确拒绝执行，不代表网络超时后可以不做业务去重直接重发。未知执行结果仍需结合业务幂等键和实际 SDK 行为处理。
- 多进程有限任务全部完成，不是长期吞吐、任意调度下严格均分或生产容量的证明。
- 公共 API 不返回 Redis 发放时间。示例用获取前后的时间界定发放区间，无法确定的边界明确列出；本轮没有为观测用途扩展公共 API。

## 报告怎么看

`target/latest-report.json` 保存最新汇总；每个 `target/run-*` 目录保存实际 HTTP 事件、每个 JVM 的日志与逐次获取区间。

`uncertain_boundary_groups` 不为零表示公共接口测量无法确定该边界，应结合精确 Lua 合约测试理解。`observed_http_window_pass=false` 表示下游到达窗口实测超限。压力场景允许报告 WARN；留余量的 `fleet` 和 `retry-paced` 场景若 HTTP 窗口超限，则测试直接失败。

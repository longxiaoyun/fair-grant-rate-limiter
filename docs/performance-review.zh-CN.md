# 性能与稳定性实测（修复前基线）

以下是 v3 修复前的历史基线；当前修复结果见[修复后复测](performance-fix.zh-CN.md)。

本次验证发现：**低配额、多节点公平分发的场景通过了短期故障验证；高配额、单桶竞争存在明显的轮询瓶颈。** 以下结果来自本机实跑，不是生产容量承诺。

测试版本：基于 `9fb4a03` 的库代码，仅增加独立压测客户端。环境为 macOS 26.5.2 / arm64、14 个逻辑 CPU、Temurin Java 21.0.9、Redis 8.0.2，本机 TCP。每个 JVM 使用 16–128 MiB 堆、Serial GC。性能测试关闭 Redis 持久化，故障测试启用 AOF everysec。

## 性能

每个案例预热 3 秒，测量 10 秒，运行两轮，第二轮反向执行；协作重试案例另外运行两轮。表格为两轮范围。获取耗时包含连接池、网络、Lua 和解析。所有性能案例均为零 ERROR、零 Redis 故障拒绝。

| 场景 | 获取调用/秒 | 实际获准/秒 | 获取耗时 P95 |
|---|---:|---:|---:|
| 单线程、单桶，普通令牌桶 | 3,824–4,225 | 3,824–4,225 | 0.29–0.35 ms |
| 单线程、单桶，加滑动窗口 | 4,108–4,228 | 4,108–4,228 | 0.28–0.30 ms |
| 30 线程竞争一个桶，连续申请 | 17,307–18,469 | 1,136–1,223 | 2.06–2.25 ms |
| 30 线程竞争一个桶，遵循重试提示 | 584–589 | **35.8–36.2** | 3.05–3.39 ms |
| 30 线程、100 个桶，默认借出校验 | 15,490–16,022 | 15,348–15,874 | 2.40–2.51 ms |
| 同上，关闭借出 PING | 22,273–22,869 | 22,065–22,656 | 1.74–1.83 ms |
| 单线程、5,000 个桶 | 3,772–4,132 | 3,772–4,132 | 0.30–0.36 ms |

性能案例把 rate、burst 和窗口上限设得很高，避免配额成为瓶颈。大量 WAIT 不能算成成功处理能力。100 桶案例和连续申请案例用于测实现开销；业务代码仍应正确处理 WAIT。

### 已确认的调整方向

1. **单桶轮询需要优化。** 令牌充足但尚未轮到当前客户端时，Lua 固定建议等待最多 50ms。FIFO 队首只能在下一次轮询时推进，因此客户端越多，高配额桶越容易被等待时间限制。不能仅调大 rate 就获得相应吞吐。后续实现应允许配置或自适应调整这段等待，并同时验证 Redis 请求量、低配额负载和公平性。本次没有修改算法；该瓶颈仍然存在。
2. **借出 PING 有可测量开销。** 100 桶案例关闭 `testOnBorrow` 后，有效吞吐提高约 43%–44%。默认校验策略保持不变；需要吞吐的使用者可以通过外部连接池调整，并在自己的网络和连接生命周期条件下验证。
3. **高基数资源需要状态生命周期。** 5,000 个资源在回执过期后仍保留 10,000 个 key，Redis 用量约 3.32 MiB。桶与窗口状态不随闲置自动删除，这是现有行为，不能直接称作内存泄漏。资源名无限增长时需要治理；删除仍可能使用的桶会重置配额，不能简单定期扫删。
4. **200ms 不是完整调用超时。** 默认借出校验的故障测试中，单次获取最大约 622ms；连接池等待、连接校验及命令执行可能叠加。业务需要自己的整体超时和取消策略。

## 稳定性与故障恢复

30 个独立 JVM 共享一个桶：rate=5、burst=1，任意滑动 15 秒最多发放 75 个令牌。依次终止一个 JVM、断开 Redis 连接、清空脚本缓存、暂停 Redis 3 秒、正常停机 2 秒后从同一 AOF 重启。

| 指标 | 默认借出校验，180 秒 | 关闭借出校验，90 秒 |
|---|---:|---:|
| 成功发放 | 835 | 402 |
| 存活节点各自获准次数 | 28–29 | 13–14 |
| Redis 不可用时拒绝 | 521 | 551 |
| ERROR / 降级放行 | 0 / 0 | 0 / 0 |
| 确定超发 / 边界不确定组 | 0 / 0 | 0 / 0 |
| 故障稳定区间内成功获取 | 0 | 0 |
| Redis 恢复运行后首次新获取成功：暂停 / 重启 | 242 / 37 ms | 212 / 94 ms |
| 获取耗时 P95 / P99 | 8.15 / 13.15 ms | 7.04 / 201.73 ms |
| 最大获取耗时 | 622 ms | 211 ms |

两轮中，29 个存活节点均在最后一次重启后重新获得令牌。关闭校验的测试时间更短，故障占比更高，不能直接比较两轮 P99 来判断哪种连接池策略更好。

窗口检查使用每次公共 API 调用开始与成功返回的时间界限，不访问库内部 Redis key。故障检查排除切换时已经在途的请求。Redis 短暂停顿期间客户端拒绝获取；恢复后的首次成功均落在检查阈值内。

默认配置的 180 秒测试中，Redis 采样峰值约 1.78 MiB，结束且回执过期后约 1.24 MiB，只剩两个状态 key。堆、GC、CPU 与每秒 Redis 采样均保存在原始报告中。数分钟的数据只能用于发现明显异常，不能证明不存在缓慢泄漏。

## 复现与边界

运行命令、负载定义和指标口径见[验证脚本说明](../examples/quickstart/LOAD_TESTS.md)。压测仅操作自动启动的隔离 Redis，不连接已有服务。

尚未覆盖：跨机器网络延迟、Redis Cluster/Sentinel 故障转移、异常断电与 AOF 数据丢失、长时间运行、生产规模的资源数和并发数。此次正常停止再启动保留状态，不能用它证明数据丢失后仍然不会超发。建议上线前在目标环境延长运行时间，并按实际桶数量、配额和网络条件复测。
